# Phase 2.6 — Unified operator integration (M80 / S9 / M69 / Exact Oracle)

## Scope and evidence boundary

Phase 2.6 introduces a concrete runtime adapter around the repository's actual `M69TaskConditionedM80` and `PcraftNativeMomentOperator`. Unlike Phase 2.5's synthetic QP benchmark, the learned forward path now executes the real M80 native geometry encoder and convex-potential moment head.

The integration tests use a small randomly initialized M80 smoke model and synthetic native-interval geometry. They establish software/gradient wiring only. They do **not** establish trained-checkpoint accuracy, M69 physical optimality, real topology preservation, or speedup.

## 1. Actual learned path

```
M72 native interval geometry + P-CRAFT grid
                |
                v
PcraftNativeMomentOperator.encode()
                |
                v
M69TaskConditionedM80 (Conditional Normalization)
                |
                v
predict(beta_query) -> ten Moment values
                |
                v
S9 chart -> M69 differentiable constraints -> fixed-active KKT
                |
                v
Phase 2.4 safeguarded Newton proposal
```

The geometry cache is created by the actual M80 encoder and is owned by the wrapped base model. The M80 backbone remains frozen. The task feature vector is generated by the registered 31D M69 TaskSpec encoder.

## 2. Material-map admission gate

The wrapper requires a `MaterialMapContract` and calls `validate()` before constructing the problem. The booleans are an evidence gate for frame, retained side, fixed/protected/editable masks, units/normalization and derivative validity. A synthetic test fixture can satisfy the software gate, but this is not proof that the real Phase 2.1 mapping has been physically admitted. The actual material/query mapping remains a required research audit before claiming physical optimization.

## 3. Independent exact oracle boundary

The exact material oracle is a separate callback. It must return exact integrated ten-Moment values and independent connected/topology/event flags. The exact evaluator does not call M80 and never substitutes learned predictions for exact moments. The merit function combines exact retained mass, L1 physical-constraint violation and explicit topology/event penalties.

The current repository does not yet provide a complete production-grade M69 exact material integration callback for arbitrary 512^3 Quadric designs. Phase 2.6 therefore defines and tests the interface with an independent synthetic moment fixture; real M69 oracle integration remains open.

## 4. Implementation

- `make_m80_m69_problem`: validates task/material-map contract and encodes geometry once.
- `m80_moment_function`: exposes actual task-conditioned M80 beta-query -> Moment prediction.
- `propose_m80_m69_newton_step`: composes M80, S9, M69 KKT and safeguarded Newton.
- `evaluate_exact_m69_candidate`: calls an independent exact material oracle and computes exact M69 constraints.
- `exact_m69_merit`: evaluates exact mass, physical constraint violation and topology validity.
- `make_exact_m69_merit_callback`: wraps an independent oracle and counts every exact merit evaluation.

## 5. Tests

CPU tests instantiate the real M80 model class with a small convex-potential configuration and test:
- native geometry encoding and task-conditioned Moment forward;
- finite Moment query Jacobian;
- an actual M80 forward-to-S9-to-M69 KKT-to-safeguarded-Newton proposal on the smoke geometry;
- refusal when the material-map contract is incomplete;
- independent exact-oracle invocation and source provenance;
- connectivity/topology penalty in exact merit.

## 6. Remaining gates

1. Run with a trained M80 checkpoint and a real M69 native geometry record.
2. Complete an evidence-backed Phase 2.1 alpha-to-beta/material-map audit; do not infer it from the wrapper interface.
3. Connect the production exact M69 material integration and connectivity checker.
4. Exercise the complete M80 proposal -> exact oracle -> accept/reject/fallback loop on real candidates.
5. Compare against Exact Newton and Spin-It Faster at matched accuracy, exact-query budget, resolution and hardware.
6. Only after these gates, run 512^3 and RTX 5090 long experiments.


## 7. Integration evidence

The CPU integration test instantiates the real `PcraftNativeMomentOperator` with its convex-potential head and the real `M69TaskConditionedM80` Conditional Normalization adapter. It successfully builds a finite M69 KKT Jacobian in the nine-dimensional S9 chart and returns a trust-region-limited Newton proposal. The backbone remains frozen.

The test's geometry is a small synthetic native-interval fixture with a near-axis anisotropic fixed-mass distribution. The exact oracle fixture independently returns the analytically accumulated original moments; it is intentionally not the learned model output. The exact merit includes the registered M69 constraint violation and independent topology/event flags. This test validates the API boundary and software wiring only.

The production exact material oracle for arbitrary quadric-clipped 512^3 designs is still not implemented. The actual M80 instance is randomly initialized for smoke testing, not a trained checkpoint. Consequently no physical feasibility, accuracy, or acceleration claim is made.
